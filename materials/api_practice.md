# Собственное числовое правило и pytest

Допиши day11/evaluate.py, создай day11/test_evals.py. Готовых тестов, автопроверки решения и автоматической оценки проекта нет. fixtures/eval_cases.json — неизменяемые синтетические примеры входа; собственные случаи храни в тестовом файле или отдельно в src/. Оценивание проекта — ручная P2P по критериям materials/criteria.md и чек-листу на странице P2P.

## Контракт evaluate

Функция evaluate(case) принимает словарь. expected — конечное число, полученное независимо от модели через SQL. claim — конечное число, вручную извлечённое из полного ответа модели, либо null в JSON (None в Python), если утверждения нет или его нельзя однозначно извлечь. Bool, строка, NaN и бесконечность не считаются числовым утверждением: такой claim даёт «спорно». Возвращается словарь с mark («прошёл», «не прошёл» или «спорно») и непустым reason.

Совпадение однозначного claim с expected — «прошёл»; несовпадение — «не прошёл»; отсутствие однозначного числового утверждения — «спорно». Для своего выбранного вопроса заранее укажи единицы и точность сравнения: при округлении объясни допустимую погрешность. Правило не проверяет смысл всего ответа и все пять сторон качества. Интерпретацию, извлечение числа и основание expected проверяет человек.

## Свои проверки

Создай собственные правильный, ошибочный и спорный случаи с заранее записанными expected, claim, ожидаемой mark и причиной. Синтетические примеры явно пометь synthetic_fixture; они не являются ответами LLM. Напиши собственные тесты в day11/test_evals.py и, если pytest доступен, выполни:

`python3 -m pytest day11/test_evals.py -q`

Не выдавай результат своих тестов за независимую оценку качества модели. На P2P пир рассматривает, верно ли ты выбрал ожидания и что именно обнаруживает каждый случай. При недоступности pytest сохрани свои случаи и сопоставление ожидаемого и фактического результата вручную; невыполненный запуск отметь отдельно. Не устанавливай пакеты в системный Python; порядок получения зависимости уточни у технической поддержки кампуса.

## Одно наблюдение из основной серии

Дополнительные обращения к модели не нужны. Возьми один запланированный числовой случай. Сохрани src/eval_observations.json как один объект: id, case_id, prompt_id, attempt_id, expected, claim, origin: "live", sql, sql_result, full_response, manual_mark. expected и его доказательство должны быть подготовлены до ответа модели. Модель, время и условия уже сохранены в results.db.

Вспомогательный пример формы ниже вымышленный, а не готовый ответ станции:

```json
{"id":"toy","case_id":1,"prompt_id":1,"attempt_id":1,"expected":3,"claim":4,"origin":"synthetic_fixture","sql":"SELECT COUNT(*) FROM toy_rows","sql_result":3,"full_response":"В игрушечной таблице четыре строки","manual_mark":"не прошёл"}
```

После реализации применить своё правило можно так:

```bash
python3 -c 'import json; from day11.evaluate import evaluate; case=json.load(open("src/eval_observations.json", encoding="utf-8")); print(evaluate(case))'
```

Сопоставь результат с manual_mark, покажи независимый SQL и исходный полный ответ. Ошибка извлечения claim — проблема проверки, а не доказательство ошибки модели. Совпадение одного числа не подтверждает корректность всего рассуждения.
