# Открытые критерии Д11

Работу разбирает пир. Чек-лист находится на странице P2P проекта; готовых тестов и автоматической оценки проекта нет. Каждый критерий оценивается отдельно, бонусы отдельно.

## Задание 1. Сначала проверь себя

- Запросы из src/explore.sql выполняются без ошибок, перед каждым есть комментарий о том, что означает одна строка результата.
- Результаты верны.
- Заметка «Знакомство с базой» объясняет разницу между руководителем и участником, NULL и нулём, отсутствием осмотра и исправностью прибора.

## Задание 2. Ошибка в чём…

- Есть пять заметок «Разминка»; в каждой названы ошибка, доказательство строками базы и сторона качества, которую оценить нельзя.
- Есть пять правил оценки, по одному на каждую сторону качества; в каждом указаны успех, ошибка и спорный случай, и правило можно применить без пояснений автора.
- Автор своими словами объясняет, чем различаются пять сторон качества.
- Реализовано числовое правило; созданы собственные правильный, ошибочный и спорный случаи. Ожидания и фактические результаты объяснены; запуск pytest или техническое препятствие зафиксированы. Готовых тестов нет.
- src/eval_observations.json содержит expected из независимого SQL, полный ответ, claim, origin и ручную отметку; результат evaluate сопоставлен с ручным. Синтетические случаи не выданы за live ответы, новых обязательных вызовов модели нет.

## Задание 3. Подготовь ловушки

- В журнале 10 случаев и 12 формулировок — обычный и трудный случай на каждую из первых четырёх сторон качества и 2 случая на устойчивость с двумя формулировками одного смысла.
- Ожидание и доказательство записаны до первого запуска модели.
- На случае, выбранном проверяющим, автор выполняет свой доказательный SQL и обосновывает ожидаемый ответ без модели. Для неоднозначного вопроса у него есть два толкования, для вопроса без данных — список недостающих сведений.
- Трудности в случаях разные, вопросов из разминки среди них нет.

## Задание 4. Первый прогон

- На каждую из 12 формулировок есть попытка этапа main; во всех попытках одна модель, в условиях указаны дата, новый чат и настройки.
- Ответы сохранены целиком; SQL модели выполнен программой, результат или текст ошибки сохранён; автор отличает текст модели от результата выполненного запроса.
- Каждая оценка по основной стороне качества обоснована строками или расчётом; обе пары устойчивости оценены целиком; сбои сервиса отмечены как «спорно» с причиной.
- Правильные ответы модели тоже сохранены и оценены, а не только удачные атаки.

## Задание 5. Ещё раз

- У двух выбранных случаев по 3 ответа на исходную формулировку с той же моделью и контекстом; у сокращённой формулировки (shortened) 2 ответа. Плановая серия — 18 ответов; дополнительные попытки и исключённые записи ввода объяснены по ID.
- Заметка «Повтор и сокращение» содержит номера формулировок, что убрано и осталась ли ошибка; повторы не смешаны с перефразированием, выводов о модели «в целом» нет.

## Задание 6. Что говорят числа

- python3 src/report.py запускается из корня, открывает src/results.db только для чтения, SQL лежит в src/report.sql, сторонних библиотек нет.
- В отчёте есть все пять пунктов README. Доля ошибок = fail / (pass + fail); unclear и na выведены отдельно; при нулевом знаменателе — «нет данных»; рядом с долей видно число наблюдений.
- Нет двойного счёта. Ответы не размножены соединением с оценками; пара — одна оценка; peer и defense показаны отдельно; сокращённая формулировка исключена из пунктов 2–4. Основные оценки отбираются по cases.dimension_id; дополнительные отдельно. Исключённые технические записи указаны по ID с причиной.
- Строка отчёта совпадает с независимым ручным подсчётом по attempt_id/pair_id; автор объясняет единицу счёта и одно действие SQL. Интерпретация и ошибка вычисления различаются.
- На пустом журнале (например, на временной базе из data/journal_schema.sql) программа не падает.

## Задание 7. Чужой взгляд

- Обмен проведён — в журнале 2 ответа этапа peer с моделью и условиями собеседника (всего не меньше 20 ответов). Либо есть src/exchange.md с двумя вопросами и контекстом, и обмен проведён на этой встрече.
- В заметке «Обмен» есть псевдоним собеседника, номера случаев, совпадения и расхождения; вторая оценка того же ответа записана с причиной.
- Итоговая заметка называет самую слабую сторону качества, ошибку, которая могла бы повлиять на решение человека, места, где наблюдений мало, и следующий шаг; выводы опираются на собственные наблюдения.

## Задание 8. Bonus. Попробуй исправить

- Есть src/defense.txt и 6 попыток этапа defense (выбранный случай и два обычных, по 2 ответа) с полным изменённым контекстом и оценками.
- Заметка сравнивает результаты до и после и не скрывает ухудшений на обычных случаях.

## Задание 9. Bonus. Проверь проверяющего

- В заметке есть обе оценки с причинами, уточнённое правило и переоценка этого ответа и ещё двух; исходные оценки не изменены.
- Автор объясняет, где была проблема — в модели, в вопросе или в правиле оценки.
